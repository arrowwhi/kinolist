# kinolist

Телеграм-бот и мини-приложение для коллекции фильмов, которые попадаются в
рилсах Instagram.

Кидаете боту ссылку на рилс — сервис достаёт подпись, распознаёт название,
находит карточку в кинобазе и спрашивает, тот ли это фильм. Можно и просто
написать название текстом. Вся коллекция с жанрами, описаниями, статусами и
оценками — в мини-приложении внутри Telegram.

## Что внутри

- Один Go-бинарь: HTTP API, Telegram-бот и фоновый воркер обогащения.
- PostgreSQL: коллекция, очередь задач, состояние диалога, кэш каталогов.
- React + TypeScript мини-приложение, встроенное в бинарь через `embed`.
- Чистая архитектура: `domain` → `usecase` → `repository` / `transport` → `app`.

Нетривиальные решения задокументированы в [`docs/adr/`](docs/adr/), контракт
API — в [`api/openapi/openapi.yaml`](api/openapi/openapi.yaml).

## Требования

- Go 1.26+
- Node.js 22+ (для сборки мини-приложения)
- Docker и Docker Compose
- Токен бота от [@BotFather](https://t.me/BotFather)
- Ключ [TMDB](https://www.themoviedb.org/settings/api) — бесплатный

## Быстрый старт

```bash
cp .env.example .env      # заполните TELEGRAM_BOT_TOKEN, TMDB_API_KEY, POSTGRES_DSN
make compose-infra        # postgres + миграции
make run                  # сервис на :8080
```

Для локальной разработки с горячей перезагрузкой: `make dev` (нужен `air`,
ставится через `make tools`). Фронтенд отдельно — `make web-dev`.

Без ключей `INSTAGRAM_API_KEY` и `LLM_API_KEY` сервис работает: ссылки на
рилсы отклоняются понятной ошибкой, добавление по названию доступно
полностью.

## Настройка бота

1. `@BotFather` → `/newbot`, получите токен.
2. Разверните сервис на домене с валидным HTTPS (см. ниже). Mini App без
   HTTPS не откроется.
3. `@BotFather` → `/newapp` → укажите тот же домен.
4. В `.env`: `PUBLIC_URL=https://ваш-домен`, `TELEGRAM_MODE=webhook`.

Локально удобнее `TELEGRAM_MODE=polling` — публичный адрес для самого бота
тогда не нужен (но нужен для Mini App, например через `cloudflared tunnel`).

## Деплой

```bash
cd deployments
DOMAIN=kino.example.com docker compose -f compose.prod.yml up -d --build
```

Caddy сам получит и будет продлевать сертификат Let's Encrypt. Миграции
накатывает отдельный контейнер до старта приложения.

Служебные эндпоинты: `/healthz` (liveness), `/readyz` (readiness, проверяет
БД), `/metrics` (Prometheus). `/metrics` наружу не выставляется — Caddy
отдаёт на него 404.

## Как это работает

1. Ссылка или название попадают в `enrichment_jobs` со статусом `pending`,
   пользователю сразу уходит ответ.
2. Воркер забирает задачу через `FOR UPDATE SKIP LOCKED`, для ссылки —
   скрапер и распознавание названия по подписи.
3. Поиск в TMDB, при пустом результате — в Кинопоиске.
4. Если название и год совпали — предлагается один вариант, иначе до пяти
   на выбор. Правило описано в [ADR-4](docs/adr/0004-match-confidence.md).
5. Подтверждение одной транзакцией пишет карточку фильма, жанры, запись
   коллекции и закрывает задачу.

Состояние диалога с ботом хранится в БД, а не в памяти: перезапуск сервиса не
роняет висящие подтверждения.

## API для обновлённого дизайна

- `GET /api/v1/movies?status=watched&genre_ids=18&q=дюна`: `total` учитывает поиск;
  `summary.movie_count`, `rated_count`, `average_user_rating` учитывают только пользователя,
  статус и жанры, независимо от `q`, `limit`, `offset`. Средняя — по просмотренным с личной
  оценкой; при отсутствии оценок — `null`. Сортировка дополнительно поддерживает
  `sort=user_rating` и `sort=watched_at`, записи без значений всегда в конце.
- `GET /api/v1/genres?scope=collection`: жанры из коллекции пользователя с
  `want_to_watch_count` и `watched_count`. Без `scope` остаётся обычный справочник.
- `PATCH /api/v1/movies/{id}`: независимые `note` и `review`; отсутствие поля оставляет
  его прежним, пустая строка очищает. Отзыв — до 5000 символов. `user_rating: 0` снимает
  оценку. Возврат в `want_to_watch` очищает дату просмотра, но сохраняет заметку, отзыв и
  оценку; эта оценка не включается в статистику просмотренных. Дата просмотра задаётся
  сервером, изменение отзыва/оценки её не меняет.
- `GET /api/v1/jobs/{id}/candidates/{provider}/{external_id}`: полная карточка выбранного
  кандидата, включая жанры, оригинальное название, длительность и метаданные рейтинга.
  Кандидат должен принадлежать задаче текущего пользователя в статусе `confirming`.
  До сохранения `id` в карточке равен 0. Успешные подробности кэшируются в памяти на
  15 минут (до 256 записей); TMDB также использует существующий кэш ответов.
- `POST /api/v1/jobs/{id}/confirm`: прежние `provider`, `external_id` плюс необязательные
  `status`, `user_rating`, `note`, `review`. По умолчанию — `want_to_watch`. Добавление,
  личные поля и закрытие задачи сохраняются одной транзакцией. Подробности загружаются
  до транзакции; сбой каталога не мешает сохранить уже найденные данные.
- В `409 already_in_collection` есть `existing_user_movie_id` для открытия существующей
  записи. Обычная обработка кода ошибки остаётся совместимой.
- Карточка фильма содержит `runtime_min`, `rating_provider` и nullable
  `rating_vote_count`. Рейтинг и число голосов всегда относятся к одному каталогу.
  Неизвестную длительность/число голосов следует скрывать, а не подменять нулём.
  Данные каталога — снимок, они не обновляются при каждом открытии карточки.

### Применение схемы и дозаполнение старых фильмов

Перед запуском обновлённого приложения применить миграции `00008` и `00009`
существующей командой миграции. Они добавляют отдельный отзыв, индекс по дате просмотра,
источник рейтинга и число голосов. Существующие заметки в отзывы не переносятся.
Для старых записей с обоими внешними ID источник рейтинга остаётся неизвестным до
дозаполнения, чтобы не ошибиться в подписи.

Дозаполнение запускается отдельно, с настроенным `.env` / окружением:

```sh
# Только показать ID, без изменения данных:
go run ./cmd/backfill --limit=100
# Получить подробности каталога и обновить только метаданные фильмов:
go run ./cmd/backfill --apply --limit=100
# Следующая партия:
go run ./cmd/backfill --apply --limit=100 --after-id=123
```

Команда не меняет пользовательские статусы, заметки, отзывы и оценки. При ошибках
сначала повторить неудачную партию, затем продвигать `after-id`. Пропущенные внешним
каталогом поля могут остаться неизвестными и после дозаполнения.

### Фильмы и сериалы

Миграция `00010_media_types.sql` добавляет `media_type` (`movie` / `tv`) и
nullable `season_count`; уникальность TMDB ID теперь учитывает тип. Деплой
через production Dockerfile автоматически применяет миграцию перед стартом.
Для пустой базы backfill не нужен. Существующие записи по умолчанию считаются фильмами;
для ранее сохранённых сериалов из Кинопоиска тип потребуется отдельно уточнить.

- `GET /api/v1/movies?media_type=tv` — только сериалы; без параметра — оба типа.
- `GET /api/v1/genres?scope=collection&media_type=tv` — счётчики жанров сериалов.
- Кандидаты, карточки и записи коллекции содержат `media_type`, `season_count`.
- Подробности: `GET /api/v1/jobs/{id}/candidates/{provider}/{media_type}/{external_id}`.
- В `POST /api/v1/jobs/{id}/confirm` передавайте `media_type` выбранного кандидата.
  Старый адрес подробностей и подтверждение без типа поддерживаются только при
  однозначном кандидате: совпавшие ID фильма и сериала требуют указать тип.
- Общий поиск TMDB исключает людей; число сезонов запрашивается при выборе сериала
  и сохраняется при подтверждении. Спецвыпуски исключаются; неизвестное число — `null`.
- Сезоны — снимок каталога на момент добавления, автоматической синхронизации нет.
- `summary.movie_count` сохраняет прежнее имя для совместимости, но считает записи
  обоих типов; тип и жанры учитываются, поисковый запрос и пагинация — нет.
- Статус, оценка и отзыв относятся к сериалу целиком; отдельного прогресса сезонов нет.

Веб-клиент показывает тип и сезоны, передаёт тип при выборе и подтверждении,
поддерживает фильтр типа в коллекциях и жанрах. Статистика рассчитывается сервером.

### Статистика главной страницы

`GET /api/v1/statistics` с обычной авторизацией Telegram возвращает:

```json
{"total_count":42,"want_to_watch_count":24,"watched_count":18}
```

Счётчики включают все фильмы и сериалы только текущего пользователя и не зависят
от параметров списков, поиска и пагинации. Каждый сериал — одна запись.
Для пустой коллекции возвращаются нули; сумма двух статусов равна общему числу.
Все значения вычисляются одним SQL-запросом, ответ не кешируется. Новая миграция
не нужна. Это отдельная статистика главной; `summary` в списках по-прежнему
учитывает фильтры. Фронт должен обновлять статистику после добавления, удаления
или изменения статуса записи.

### Режиссёры

- `GET /api/v1/directors?q=Denis&media_type=movie&sort=average_user_rating&order=desc` — режиссёры только своей коллекции, с пагинацией `limit`/`offset` и `total`.
- `GET /api/v1/directors/{id}?media_type=tv` — имя и личная статистика. Средняя считается по просмотренным работам с оценкой; без оценок — `null`. Поиск по имени не меняет статистику карточки, фильтр типа — меняет. Сериал считается одной работой.
- `GET /api/v1/movies?director_ids=17,25` — работы любого выбранного режиссёра. С жанрами и типом фильтр объединяется через AND. `summary` учитывает фильтры, но игнорирует поиск и пагинацию.
- `GET /api/v1/genres?scope=collection&director_ids=17&media_type=movie` — жанры и их счётчики внутри выбранной группы.

Карточки и предпросмотр содержат массив `directors`. В предпросмотре возвращаются внешние ID, внутренний `id` появляется при подтверждении. Совпадение имён не объединяет разных людей или записи разных каталогов. Данные сохраняются вместе с фильмом в транзакции; ошибка получения титров не мешает сохранению и не стирает известные связи. У сериалов TMDB используются aggregate credits всех сезонов, у Кинопоиска — staff с профессией DIRECTOR.

Миграция `00011_directors.sql` применяется существующим механизмом миграций при деплое; настройки Coolify менять не требуется. Старые записи автоматически не обогащаются: режиссёры появятся при повторном добавлении работы. Отдельный процесс обновления данных в деплой не добавлен.
